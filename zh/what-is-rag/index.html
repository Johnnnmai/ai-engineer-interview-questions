考察点

能否讲清 RAG 系统的两半（索引阶段和查询阶段），说出决定质量的环节（chunking、混合检索、re-ranking、metadata），并且知道最先出问题的通常是检索，而不是生成模型。

评分要点

  1. 一句话定义：在查询时从自有文档中检索相关片段（chunk）放进 prompt，让模型据此回答并给出引用。
  2. 索引链路：解析文档 → 切分 chunk → 对每个 chunk 做 embedding（向量化表示） → 连同 metadata（来源、日期、权限）存入向量库。
  3. 查询链路：可选的 query 改写 → 向量检索和/或关键词检索取 top-k → metadata 过滤 → re-ranking（重排序）；生成时要求只依据检索内容作答并引用，允许模型拒答。
  4. 收尾讲评估：检索和生成分开度量，因为通常先坏的是检索。

常见扣分点

把 RAG 说成“向量数据库加一个 LLM”，跳过解析、chunking、metadata 和 re-ranking。

参考回答

RAG 有两条链路。索引阶段，我解析文档、切成 chunk、对每个 chunk 做 embedding，并把向量和来源、日期、权限等 metadata 一起存储。查询阶段，我可以先改写 query，再做 embedding，用向量检索和/或关键词检索取 top-k，做 metadata 过滤和 re-ranking，最后把最好的几个 chunk 放进 prompt，要求模型只依据这些内容回答并标注来源。

切分时我按文档结构（标题、段落、代码块、表格行）而不是固定字符数，一般几百个 token，适度重叠。当查询里有精确的编号、产品代码或报错信息，embedding 容易把它们模糊掉，这时我用混合检索；再用 cross-encoder 重排序器在较宽的候选集（比如 top 50）里挑出最好的 5 到 10 个。

我会把检索和生成分开评估。RAG 出错时，通常先错在检索：取错了 chunk 或者漏了 chunk，而不是生成模型。

常见追问

RAG 系统应该怎样决定回答“我不知道”？ 综合多个信号：检索或重排序分数低于校准过的阈值、没有任何 chunk 能回答问题、再加一个把草稿答案和来源逐条核对的校验步骤。同时在 prompt 里明确告诉模型拒答是可以接受的。
