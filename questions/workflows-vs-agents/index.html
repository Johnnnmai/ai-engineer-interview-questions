What the interviewer is testing

Whether you can choose the simplest architecture that solves the task, and explain the predictability, cost and testing differences.

Answer framework

  1. Workflow: code defines the steps (classify, retrieve, draft, check); the LLM fills specific steps.
  2. Agent: the model decides which steps to take and in what order, using tools in a loop.
  3. Choose a workflow when the path is known: it is cheaper, faster, easier to test and to audit.
  4. Choose an agent when the path depends on what is discovered, such as open-ended research or debugging.
  5. Hybrid: a workflow with one bounded agentic step is often the best fit.

Sample answer

The difference is who controls the path. In a workflow my code decides the sequence: for example, classify the ticket, retrieve the policy, draft a reply, check it against rules, send it for review. The model does specific jobs inside fixed steps. In an agent, the model decides what to do next, which tool to call and when it is finished.

I default to workflows when I can write the steps down, because they are predictable. Each step can be tested on its own, costs and latency are bounded, and it is easy to explain to compliance what happened. Agents make sense when the next step genuinely depends on what was found, such as investigating a production incident, where you cannot know in advance which logs or services matter.

Most real systems end up hybrid: a workflow that handles routing, permissions and final checks, with one bounded agentic step inside it, such as research with a step limit. I would start with the workflow version, measure where it fails, and add autonomy only where that failure is about needing flexible steps.

Worked example

A workflow is a path you already know: extract fields, look up the order, check the return window, draft a reply, stop. Each step is a typed function or a prompt with a schema, and the graph is yours. An agent is a model that is allowed to choose the next tool and when to stop. That is useful when the next step is not known in advance, such as an open-ended investigation across several systems.

For the returns helper, a workflow is the right default. It is easier to test, cheaper, and you can require a human click before anything with a side effect. If you instead let an agent loop, you must add a maximum step count, timeouts, and an audit log, and you will still want the same business rules encoded somewhere. In an interview, say you start with a workflow and promote a step to an agent only when the branchiness cannot be listed, not because 'agent' sounds more advanced.

Likely follow-ups

Give an example where an agent clearly beats a workflow. Debugging a failing build across an unfamiliar codebase, where each finding determines the next file or command.

Common mistakes

  • Building an agent for a task with fixed steps.
  • Assuming agents are always more capable.
  • Forgetting testing and audit requirements.
  • Not bounding the agentic part of a hybrid.
