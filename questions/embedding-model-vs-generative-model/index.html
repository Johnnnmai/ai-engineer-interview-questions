What the interviewer is testing

Whether you can explain the different outputs and jobs of the two model types and show how they combine in a retrieval system.

Answer framework

  1. Embedding model: maps a piece of text to a fixed-length vector so that similar meanings land close together.
  2. Generative model: predicts and outputs tokens to produce text, code or structured data.
  3. Uses of embeddings: semantic search, clustering, deduplication, classification and recommendations.
  4. Cost: embedding calls are far cheaper and faster, so you can embed a whole corpus once.
  5. Together: in RAG the embedding model finds candidate passages and the generative model reads them and writes the answer.

Sample answer

An embedding model turns text into a single vector of fixed length, for example a few hundred or a few thousand numbers. It is trained so that texts with similar meaning have vectors that are close by a measure such as cosine similarity. It does not write anything; its output is only useful for comparison.

A generative model produces tokens one at a time. It is what writes the answer, the summary or the SQL query.

They solve different problems and have very different costs. Embeddings are cheap enough to compute for millions of documents at ingestion, which is why they back semantic search, deduplication, clustering and simple classifiers. In a RAG system I embed every chunk once, embed each query at request time, find the nearest chunks, and only then pay for the generative model to read those few chunks and answer.

Worked example

A docs search box needs to rank 200,000 paragraphs for the query 'how do I rotate an API key'. An embedding model turns the query and each paragraph into a fixed-length vector and returns the nearest neighbors. Nothing in that step writes a sentence. A generative model then reads the top paragraphs and writes the actual how-to answer. If you skip the embedding step and ask a generative model to 'find the right doc' over the whole corpus, you have no cheap similarity index and you will miss or invent a source.

Do not treat the last hidden state of a generative model as a drop-in embedding without measuring it. It can work as a starting point, but a model trained with a contrastive or retrieval objective usually ranks short keyword queries better. Evaluate both on your own query log, not only on a public embedding leaderboard, and keep the two roles separate in the design you draw on the whiteboard.

Likely follow-ups

Can you use a generative model to create embeddings? You can take hidden states from it, but dedicated embedding models trained with contrastive objectives usually retrieve better and are much cheaper.

Common mistakes

  • Saying embeddings store the text; they store a lossy representation used for similarity.
  • Mixing embeddings from two different models in one index.
  • Using a generative model for tasks a cheap embedding classifier can handle.
  • Forgetting to re-embed the corpus when the embedding model changes.
