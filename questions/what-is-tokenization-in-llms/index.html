What the interviewer is testing

Whether you know that models see tokens, not characters or words, and can connect that to practical consequences: cost, context limits, multilingual products and strange errors.

Answer framework

  1. Define it: text is split into subword units by an algorithm such as byte-pair encoding (BPE) or a unigram model (SentencePiece), and each unit maps to an ID.
  2. Cost and limits: pricing, latency and the context window are all counted in tokens.
  3. Languages: the same content can take noticeably more tokens in some non-English languages, which raises cost and uses more context.
  4. Failure modes: counting letters, reversing strings and long-number arithmetic are hard because the model never sees individual characters.
  5. Practical habit: measure token counts with the model's own tokenizer when budgeting prompts.

Sample answer

Tokenization turns text into the integer IDs the model actually reads. Modern LLMs use subword tokenizers such as BPE: frequent words become a single token, rarer words are split into pieces, and anything can still be represented through byte-level fallbacks.

It matters in three practical ways. First, everything is metered in tokens: price, latency and the context window. Second, token efficiency differs by language and by content type, so a product serving several languages, or a lot of code or JSON, can cost more per request than an English-only estimate suggests. Third, it explains failures that look odd from the outside. A model may miscount the letters in a word or slip on arithmetic with long numbers because those characters are bundled into tokens it cannot look inside.

When I budget a prompt I count with the target model's tokenizer rather than estimating from word counts, because tokenizers differ between model families.

Worked example

Tokenization is how raw text becomes the integer IDs the model was trained on, usually with a subword scheme such as BPE or SentencePiece. The word 'unhappiness' may become several tokens, a common English word may be one, and a rare name or a piece of code may split in a surprising way. Limits that people call 'context length' are token limits, not word limits, so a 2,000-word policy can blow a 4,000-token budget once you add markup and a long system prompt.

This shows up in production in three places. Cost and truncation are counted in tokens. A user-facing character counter will drift from the model counter, especially for Chinese, code, or URLs, so log both. And a regex that assumes one token per word will fail if you try to force a phrase to be atomic. When you discuss long context or pricing in an interview, say you would measure with the same tokenizer the model uses, not with a word split.

Likely follow-ups

Why can an LLM fail to count the letters in a word? It sees tokens, not characters, so the letters inside a token are not directly visible to it.

Common mistakes

  • Assuming one token equals one word for every language and content type.
  • Estimating prompt size with one model's tokenizer and deploying on another.
  • Blaming reasoning for errors that come from tokenization, such as character-level tasks.
  • Forgetting that output tokens count toward cost and context too.
