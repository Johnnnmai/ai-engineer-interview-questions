What the interviewer is testing

Whether you choose chunking from the documents and the questions rather than defaults, and whether you can explain the size trade-off and how to measure it.

Answer framework

  1. Follow structure: split on headings, sections, paragraphs, code blocks and table rows rather than fixed character counts.
  2. Pick a size range: typically a few hundred tokens with modest overlap, then tune.
  3. Know the trade-off: small chunks match precisely but lose context; large chunks keep context but dilute similarity and cost more tokens.
  4. Use parent retrieval when needed: retrieve small chunks, then pass their parent section to the model.
  5. Decide by measurement: compare recall@k on real questions for each strategy.

Sample answer

I start from the documents. Policies, manuals and wikis have headings and paragraphs, so I split along that structure and keep the heading path as metadata, for example 'Billing > Refunds > Annual plans'. Code is split by function or class, and tables by row with the header repeated, so each chunk still makes sense when read alone.

Then I choose a size, usually a few hundred tokens with a small overlap. Small chunks give sharper matches because the embedding represents one idea, but the model may not get enough context to answer. Large chunks carry more context but blur the embedding and use more of the prompt. A common compromise is small-to-parent retrieval: match on small chunks, then send the enclosing section to the model.

I do not settle this by intuition. I build a set of real questions with the passages that answer them, index the corpus with two or three strategies, and compare recall@k and final answer quality. The winner is often different for different document types.

Worked example

A 40-page policy PDF split into fixed 200-character windows will cut a rule in half: the condition is in chunk 14 and the restriction is in chunk 15, and retrieval may return only one of them. A better default follows structure: headings, paragraphs, list items, code blocks, and table rows, with chunks often in the few-hundred-token range and a small overlap so a sentence at a boundary is not lost.

There is no universal size. Short, dense FAQ items can be one section each. Long narrative pages may need 400 to 800 tokens with overlap. After you pick a scheme, measure recall@k on real questions and read the misses. If the miss is a split table, chunk by row and keep the column headers in every row. If the miss is an identifier that appears only in a title, put the title in the chunk text or in metadata. Tune with those measurements, not with a blog post's favorite character count.

Likely follow-ups

What goes wrong with fixed-size chunking? It cuts sentences, tables and code mid-way and separates headings from their content, so chunks lose meaning and retrieve poorly.

Common mistakes

  • Using a library's default chunk size without testing.
  • Splitting tables and code blocks in the middle.
  • Dropping headings and document titles that give chunks context.
  • Judging chunking by answer quality alone instead of retrieval recall.
