How do you evaluate a RAG system?

How to answer it in an AI engineer interview: what is being tested, a step-by-step framework, a sample answer and the mistakes to avoid.

What the interviewer is testing

Whether you split evaluation into retrieval and generation, know concrete metrics for each, build a golden set from real questions, and can trace a failing answer to the stage that broke.

Answer framework

  1. Evaluate retrieval and generation separately.
  2. Retrieval: recall@k, precision@k, MRR or nDCG against labelled question-to-source pairs.
  3. Generation: faithfulness (claims supported by the retrieved context), answer relevance, correctness against a reference, citation accuracy.
  4. Data and grading: a golden set from real user questions, an LLM judge calibrated against human labels, plus latency and cost per answer.
  5. Debugging: trace a failing question stage by stage and fix the earliest failing stage.

Sample answer

I evaluate it in two parts. For retrieval I use recall@k, precision@k, MRR or nDCG against labelled question-to-source pairs. For generation I measure faithfulness, meaning claims supported by the retrieved context, plus answer relevance, correctness against a reference and citation accuracy.

I build the golden set from real user questions, use an LLM judge calibrated against human labels, and track latency and cost per answer. For faithfulness I break each answer into claims, check each against the sources and report the share supported, and I check that cited passages actually contain the claims. I also evaluate refusal precision, not only answer accuracy.

When an answer is bad, I trace it: was the right document ingested and parsed correctly, chunked sensibly, in the top-k, ranked high enough, included in the prompt, and used by the model? I fix the earliest failing stage. Most issues are parsing, chunking or retrieval, not the generator.

Likely follow-ups

How do you debug poor RAG answer quality? Trace a failing question through ingestion, parsing, chunking, retrieval, ranking, prompt assembly and generation, and fix the earliest failing stage.

Common mistakes

  • Scoring only the final answer, so you cannot tell whether retrieval or generation failed.
  • Building the eval set from invented questions instead of real user questions.
  • Using an uncalibrated LLM judge as the source of truth.
  • Ignoring latency and cost per answer.
  • Changing the prompt or model before checking whether the right chunk was even retrieved.
