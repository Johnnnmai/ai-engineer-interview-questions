What the interviewer is testing

Whether you rely on enforcement and validation rather than prompt wording alone, and whether you design schemas that the model can fill correctly.

Answer framework

  1. Enforce the format: use the provider's structured output or JSON-schema mode, or constrained decoding (grammar-guided generation) when self-hosting.
  2. Validate every response against the schema in code, for example with Pydantic or a JSON Schema validator.
  3. Repair on failure: retry once or twice with the validation error included in the prompt, then fall back or escalate.
  4. Design the schema: keep it flat, use enums for categories, make optional fields explicit and allow null instead of forcing guesses.
  5. Monitor the parse failure rate and the rate of empty or default values in production.

Sample answer

I treat structured output as an engineering problem, not a prompting problem. First I enforce the format at generation time: hosted APIs offer a JSON-schema or structured output mode, and with a self-hosted model I use constrained decoding so only tokens that keep the output valid can be sampled. That removes most syntax errors.

Valid JSON can still be wrong, so I validate the parsed object against a Pydantic model: types, enums, ranges and required fields. If validation fails, I send one repair attempt that includes the original output and the exact validation error, and if that also fails I return a clear error or route to a fallback instead of passing bad data downstream.

Schema design matters as much as enforcement. For an invoice extractor I would use a flat object, an enum for currency, explicit nullable fields for values that may be missing, and a short description per field. If a model is forced to fill a required field it cannot find, it will invent one, so allowing null is safer. I then track parse failures and null rates per field as quality signals.

Worked example

Ask for one schema and enforce it. Give the model a short instruction and a JSON Schema, then use constrained decoding or a grammar when the runtime supports it so the tokens must match the schema. After the call, validate with a real parser. If validation fails, retry once with the validator error, then stop and return a structured failure rather than passing a half-parsed string to a downstream service.

Keep the schema tight: required fields, enums for categories, and no free-form bag of keys. Set temperature low so the same prompt does not wander. For a ticket classifier, a typical record might be queue, severity, and summary with a maximum length. Unit-test the path with empty input, extra keys, and a truncated completion. In an interview, do not stop at 'I told it to reply in JSON'. Name schema, constraint, validation, and a retry budget.

Likely follow-ups

Why not just ask for JSON in the prompt? Prompt-only instructions work most of the time, but at scale you get truncated objects, extra prose and wrong types; enforcement plus validation handles those cases.

Common mistakes

  • Relying on a prompt instruction alone for production parsing.
  • Skipping semantic validation because the JSON parsed.
  • Making every field required, which pushes the model to invent values.
  • Retrying without telling the model what was wrong.
  • Using a high temperature for extraction tasks.
