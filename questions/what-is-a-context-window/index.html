What the interviewer is testing

Whether you treat the context window as a design constraint with a budget, not as a reason to skip retrieval or memory, and whether you know models use long inputs unevenly.

Answer framework

  1. Define it: the maximum number of tokens the model can attend to in one call, prompt plus generated output.
  2. Costs: longer prompts raise price and time to first token on every call.
  3. Quality: models use long inputs unevenly; facts buried in the middle are used less reliably.
  4. Design: decide what goes in with retrieval, summarization or memory, and give each section a token budget (system, history, retrieved context, output).
  5. Verify: test long-context behavior on your own tasks instead of trusting the advertised maximum.

Sample answer

The context window is the total number of tokens a model can attend to in one request, which includes the system prompt, conversation history, any retrieved documents and the tokens it generates. If the input fills the window, there is no room left for the answer.

A large window makes some things easier, such as reading a whole contract in one pass, but it does not remove design work. Every extra token adds cost and latency on every call, and models do not use all positions equally well; information in the middle of a long prompt is used less reliably than information at the start or end.

So I design with an explicit budget. For a support assistant I might reserve a fixed slice for the system prompt, cap conversation history and summarize older turns, give retrieved passages the largest share and leave enough room for the output. Retrieval decides what deserves to be in the window; the window size only sets the ceiling.

Worked example

The context window is the token budget the model can attend to in one request: system prompt, retrieved documents, conversation history, tool results, and the reserved space for the answer. A product advertised at 128,000 tokens does not mean you should fill 128,000 tokens. Quality often falls when the useful facts sit in the middle of a long prompt, and you still have to leave room for the completion.

A practical policy is to budget the window like memory. Keep a short, stable system prompt. Retrieve a handful of chunks, not a whole manual. Summarize old turns instead of appending the full thread forever. Count tokens with the model's tokenizer and reject or trim before you call the API, so you fail with a clear error instead of a silent truncation. In an interview, draw the budget as boxes that have to add up, and mention the reserved output tokens.

Likely follow-ups

If a model supports a million tokens, why still use RAG? Cost and latency per call, uneven use of long context, and the need for fresh, permission-filtered content all still favor retrieving only what is relevant.

Common mistakes

  • Forgetting that output tokens share the same window as the prompt.
  • Stuffing everything into a long window instead of retrieving the relevant parts.
  • Letting chat history grow without trimming or summarizing.
  • Trusting the advertised window without testing recall at different positions.
